1. Settings / Profile

One screen, five fields, one API call. Every AI prompt in the app reads the business profile, so this is the first thing a new client fills in.

Fields

FieldTypeNotes
Business nameTextRequired. Shown in prompts and meta.
LogoFile (JPG/PNG/WebP, max 2MB)Optional. Stored as a storage key in business_profile.logo_key. Can be overlaid on generated images when use_logo is checked.
WebsiteTextOptional. Included in prompt context.
LanguageSelectDefault English. Determines the language for captions and voice-overs.
About the businessTextarea (1,500 chars)Free text. This replaces tone, audience, brand story, call-to-action, and every other field. The user describes their business in their own words, and the AI reads it as context for every prompt.

How save works

1
User edits any field or picks a new logo

The floating UnsavedChangesBar appears at the bottom of the screen. It shows "You have unsaved changes" with Discard and Save buttons.

2
User clicks Save

One PUT /api/profile request as multipart form. All fields + logo (if changed) go in a single request. Not two separate calls.

3
Server handles it

If a logo file is attached: upload it to logo/<timestamp>.png in Supabase Storage, save the key. Then upsert the business_profile row (id = 1, enforced by a check constraint so a second row is impossible).

4
Bar disappears

On success, TanStack Query invalidates the profile cache, the form resets to the saved values, and the bar disappears. On failure, the bar stays with an error message.

Why one big "About" field? Earlier designs had separate fields for tone, audience, brand colors, story styles, call-to-action, etc. That's too many fields for a new client to fill in. One free-text box lets the user describe everything in their own words. The AI prompt template wraps it into the right structure.

Screen states

  • Loading: Skeleton placeholders matching the form layout (logo circle + four input skeletons).
  • Error: ErrorState component with "Failed to load profile" + Retry button.
  • Empty (first visit): The form is empty with placeholder text. The profile row already exists (migration inserts it) with empty strings.

2. Create Image

User describes an idea, picks an aspect ratio, optionally includes the logo. The image is generated by Kie in the background.

User inputs

InputOptionsSaved as
IdeaFree textmedia.idea
Aspect ratio1:1 · 4:5 · 9:16 · 16:9media.aspect_ratio
Add logoCheckboxmedia.use_logo

Execution flow

1
User fills in the dialog and clicks Generate

POST /api/media with type: "image". Creates a media row with status: "generating" and all inputs saved. Returns the row immediately.

2
API fires Inngest event

media/generate-image with mediaId. Event ID = media ID (deduplicates double-clicks).

3
Dialog closes, card appears in the grid

The media grid shows the new card immediately with a spinner and "Generating..." text. TanStack Query polls every 5 seconds while any card is generating.

4
Inngest job runs

Step 1: Load media row + business profile. Step 2: Build the image prompt (idea + profile context, handled by prompts/image.ts). Step 3: Call Kie API. Step 4: Poll for completion (with step.sleep between checks — no server runs while waiting). Step 5: Download the result. Step 6: Upload to Supabase Storage at images/YYYY/MM/<id>.png. Step 7: Mark ready.

5
Card updates

Next poll picks up status: "ready" and storage_key. The spinner is replaced by the image thumbnail. Hover shows "Create post" button.

Kie gotcha: Kie returns HTTP 200 even on failure. The job must read the code field in the response body, not just check response.ok. Task states: success, fail (with failMsg / failCode).

If it fails

onFailure writes status: "failed" and the plain error message to media.error. The card shows a red alert icon, the error message, and a Retry button. Retry calls POST /api/media/<id>/retry which fires a new event with the same saved inputs but a fresh event ID (so Inngest doesn't deduplicate it).

If the user deletes during generation

cancelOn on the job definition listens for media/deleted events matching the media ID. The run stops, no error is saved.

Concurrency

Up to 5 image generations run simultaneously. Excess requests queue.

3. Create Video

More complex than images — multiple AI steps: write script → plan scenes → generate voice-over → generate scene images → compose video.

User inputs

InputOptionsSaved as
IdeaFree textmedia.idea
Aspect ratio9:16 · 16:9 · 1:1media.aspect_ratio
Duration15s · 30s · 45smedia.duration_sec
Voice (optional)ElevenLabs voice IDmedia.voice_id

Execution flow

1
User fills in the dialog and clicks Generate

Same pattern as images: POST /api/media with type: "video". Creates row, fires media/generate-video event. Card appears with spinner.

2
Inngest job: write script

OpenAI generates a video script from the idea + business profile. The prompt is built by prompts/video-script.ts.

3
Inngest job: plan scenes

OpenAI breaks the script into visual scenes (how many depends on duration_sec). Each scene gets an image description. Built by prompts/video-scenes.ts.

4
Inngest job: generate voice-over

ElevenLabs reads the script aloud using the selected voice (or a default). Output saved to tmp/<id>/voice.mp3.

5
Inngest job: generate scene images

Each scene's description is sent to Kie in parallel (within the per-job concurrency limit). Results saved to tmp/<id>/scene-N.png.

6
Inngest job: compose video

Scene images + voice-over are combined into a video. Output uploaded to videos/YYYY/MM/<id>.mp4. Temp files in tmp/<id>/ are deleted.

7
Mark ready

Same as images: status: "ready", storage_key set. Card shows video thumbnail.

Concurrency and timeout

Max 2 video generations at once (they're expensive). 45-minute timeout per job. Each step retries up to 3 times.

4. Upload Media

User uploads their own image or video instead of generating one.

1
User picks a file

Drag-and-drop or file picker. Accepted: PNG, JPG, WebP (images), MP4, MOV (videos). Max 10MB images, 100MB videos.

2
Client requests a signed upload URL

POST /api/media/upload-url returns a signed Supabase Storage URL for images/YYYY/MM/<id>.ext or videos/....

3
Client uploads directly to storage

The file goes straight to Supabase Storage using the signed URL. The browser shows a progress bar.

4
Client registers the upload

POST /api/media with source: "uploaded", status: "ready", and the storage_key. No Inngest job needed — the file is already in storage.

5. Create Post

User picks a piece of media, selects which accounts to post to, writes captions (one per platform), and chooses when to publish.

Steps

1
User clicks "Create post" on a media card (or navigates to /posts/new)

The create post page loads with the selected media shown. If navigating from the media grid, the media ID is passed as a query parameter.

2
User picks accounts

Account list is fetched live from GET /api/accounts (Upload-Post, cached 60s). User checkmarks which accounts to post to. Each selected account becomes a post_target.

3
User writes captions

One caption editor per platform (grouped by platform, not per account — all Instagram accounts get the same caption). User can write manually or click "Generate caption" which calls POST /api/posts/captions (OpenAI, using the media's idea + business profile). Character limit shown per platform (e.g. Instagram: 2,200). "Improve" button calls POST /api/posts/captions/improve to refine an existing caption.

4
User chooses when

Three options: Draft (save without publishing), Now (publish immediately), Schedule (pick a date/time). The WhenPicker component handles this. A scheduled post creates the row with status: "scheduled" and publish_at set.

5
User clicks Create / Publish / Schedule

POST /api/posts with media_id, publish_at, and targets array (each with platform, account_id, account_name copied from the live list, caption, provider). If "Now": fires post/publish Inngest event immediately.

Captions are per-post, not per-media. The same image can be posted multiple times with different captions to different accounts. That's why captions live on post_targets, not on media.

Draft storage

An unsaved post is kept in sessionStorage via the useComposeDraft hook. This survives page refreshes within the same tab but not across tabs or browser restarts. Once the post is created, the draft is cleared.

6. Publish Flow

What happens after a post is created with "Now" or when a scheduled post's time arrives.

1
Inngest receives post/publish event

Event ID = post ID (prevents double-publishing).

2
Load post + media

Read the post with its targets. Build the media URL from the storage key. Set post status to publishing.

3
Publish to each target

Each target is its own Inngest step. For each: set target status to sending, call publisherFor(target.provider) to get the adapter, call publishPhoto or publishVideo. On success: set published + save provider_ref and url. On failure: set failed + save error message.

4
Resolve final status

After all targets are done: if all published → published. If all failed → failed. If mixed → partial.

Partial success

If 2 out of 3 accounts succeed and 1 fails, the post shows partial status. Each target shows its own status. The user can retry just the failed targets.

7. Retry, Reschedule, Edit, Delete

Retry failed media

POST /api/media/<id>/retry — reads the saved inputs (idea, aspect_ratio, etc.) from the media row, fires a new generate event with a fresh event ID. Resets status to generating, clears the error.

Retry failed post targets

POST /api/posts/<id>/retry — fires a new post/publish event. The publish job skips targets that are already published and only retries failed ones.

Reschedule a post

PATCH /api/posts/<id> with a new publish_at. Only works on scheduled posts. The scheduled post checker (Inngest cron) picks it up at the new time.

Edit a draft post

PATCH /api/posts/<id> — update captions, change targets, change publish_at. Only works on draft or scheduled posts.

Delete a post

DELETE /api/posts/<id> — deletes the post and all targets (cascade). Fires post/deleted event to cancel any in-progress job. Requires confirmation via ConfirmModal.

Delete media

DELETE /api/media/<id> — fails if any post references it (restrict FK). User must delete the posts first. Fires media/deleted to cancel any in-progress generation. Removes the file from storage.

8. Calendar

Month view of all posts with a publish_at value. Serves as a visual planning tool.

What it shows

  • Each day cell shows status chips for posts scheduled or published on that day.
  • Today is highlighted with a blue circle.
  • Empty days are clickable (navigates to /posts/new with the date pre-filled).
  • Clicking a post chip opens the post detail page.

Navigation

Left/right arrows move by month. "Today" button jumps back to the current month. Data is fetched from GET /api/posts — the same endpoint as the Posts page.

9. Connected Accounts

Shows the user's connected social accounts, fetched live from Upload-Post.

How it works

1
Page loads

GET /api/accounts → calls publisherFor("upload-post").listAccounts(). Returns platform, name, profile URL, avatar URL for each connected account. TanStack Query caches for 60 seconds.

2
User clicks "Connect account"

POST /api/accounts/connect → calls publisher.getConnectUrl(). Returns a URL to Upload-Post's connection flow. Opens in a new tab.

3
User connects on Upload-Post, comes back

The accounts page refetches on focus. The new account appears in the grid.

No connected_accounts table. Upload-Post is the source of truth. We fetch live and cache 60 seconds. When a post is created, we copy account_name onto each post_target at that moment — so the post history always shows the account name even if the account is later disconnected.

10. Error Handling

The chain

Every error passes through a fixed pipeline:

  1. Vendor returns an error — could be HTTP status, could be in the response body (Kie returns 200 + error code).
  2. Adapter translates it — the provider file (e.g. providers/publishing/upload-post.ts) catches it and throws an AppError with a type, a plain user-facing message, and a retry rule.
  3. Job converts it — toInngestError() in the job turns AppError into either NonRetriableError (permanent) or RetryAfterError (transient with a delay).
  4. Inngest retries or stops — transient errors retry the failed step (up to 3 times). Permanent errors stop the run and trigger onFailure.
  5. onFailure writes to DB — sets status to failed and saves the plain message on media.error or post_targets.error.
  6. Screen shows it — the card or row reads the error from the DB and displays it. Retry button is available.

Error types

TypeRetryable?Example
PROVIDER_DOWNYesKie API returned 500
RATE_LIMITEDYes (with delay)Upload-Post says 429, wait 30s
OUT_OF_CREDITNoOpenAI billing issue
CONTENT_BLOCKEDNoKie rejected the prompt
ACCOUNT_DISCONNECTEDNoUpload-Post API key invalid
INVALID_INPUTNoImage too large for the platform
TIMEOUTYesKie took >60s to respond
UNKNOWNYesUnrecognized error from any provider
Raw vendor errors never reach the browser. The adapter is responsible for turning "error_code: 4834002" into "Budget conflict: you can't use Campaign Budget Optimization and ad-set budget sharing at the same time." Every AppError has a message a person can understand and act on.

11. Screen States

Every screen has four defined states. Consistency prevents weird half-loaded or blank experiences.

ScreenLoadingEmptyErrorAfter reload
Media grid 8 skeleton cards (aspect-square + footer bar) Dashed border panel: "No media yet. Create an image or video with AI, or upload your own." ErrorState + Retry Generating items show spinner. Progress is not lost — Inngest owns it.
Posts table 5 skeleton rows Dashed border panel: "No posts yet. Create a post from your media library." ErrorState + Retry Publishing posts show "publishing" status. All state is in the DB.
Calendar One big skeleton (500px height) Empty day cells (no posts scheduled) ErrorState + Retry Same data as Posts — no extra state to lose.
Accounts 6 skeleton cards (avatar + two text lines) Dashed border panel: "No accounts connected." + Connect button ErrorState + Retry Refetches from Upload-Post (cached 60s).
Settings Logo skeleton + 4 input skeletons Empty form with placeholders (row exists from migration) ErrorState + Retry Form loads saved values. Unsaved changes bar only shows if inputs differ from saved.
Reload never loses progress. Generation and publishing run on Inngest. The browser only reads status from the DB. Closing the browser mid-generation is fine — the job continues server-side and the next page load shows the current state.
